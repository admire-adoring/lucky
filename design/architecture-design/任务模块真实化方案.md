# 任务模块真实化 + 推广到其余模块

> 2026-10-19。基线：任务页四个视图/四个弹窗全部走 `TaskProvider`（`pages/workspace/tasks/task-state.tsx`），
> 数据是 `data/workspace/tasks.ts` 的台账常量。后端早有 `task` 表与 5 条命令，前端没有接口层。

## 一、整体方案（三层，逐层可验证）

```
① 表       task（主，已有 16 列） + task_item（子，新增）      ← DDL + 0005 迁移
② 接口     server/task/（5 条已有命令 + item 的 3 条）          ← 读写都走这里
③ 前端     api/tasks.ts（RawTask→TaskRow 映射）+ TaskProvider   ← 组件只认 provider
```

**为什么从 provider 改起**：四个弹窗、四个视图、侧栏副标题、KPI 全部读 `useTaskApi()`。
把 provider 的 `tasks` 换成真数据、把 10 个动作换成 mutation，**上层零改动**。
这比逐个改视图可靠 —— 改视图会漏（漏的那处照常渲染旧数据，不报错）。

### 子表 `task_item`（新增，"每个任务对应多条子记录"）

| 列 | 类型 | 说明 |
| --- | --- | --- |
| `id` | TEXT PK | |
| `task_id` | TEXT NOT NULL → `task(id)` ON DELETE CASCADE | 删任务连带清子记录 |
| `title` | TEXT NOT NULL | 检查项 / 子步骤 |
| `done` | INTEGER 0/1 | |
| `sort_order` | INTEGER | 手动排序 |
| `created_at` | TEXT | |

索引：`ix_task_item_task(task_id, sort_order)`。

**为什么是"检查项"而不是评论/标签**：任务详情弹窗里最需要的"多条子记录"是**可勾选的步骤**
（"准备评审" → 发议程 / 约会议室 / 过一遍数据）。它天然 1:N、天然有完成态、天然要连带删除。
标签是 N:N（要 `task_tag` + `tag` 两张），评论要作者与时间线 —— 都比"首批改造"重。

## 四、推广模式（其余模块照着这套走）

1. **先查表**：模块的主表是否已在 DDL 里（多半在，只是没有前端接口层）；
2. **补接口层**：`api/<域>.ts`（Raw → 域模型的映射都放这一层，组件不碰列名）；
3. **补 hooks**：`use<域>` 读 + `use<域>Mutations` 写，失效一个 keys 前缀；
4. **换 provider 或页面容器**（有 Provider 的换 Provider，没有的换页面顶层的那个 hook）；
5. **派生字段不进库**：凡是"今天/逾期/落格"这类随日期变化的量，一律前端算；
6. **每步一个 `tsc`**：类型是唯一能便宜发现的"漏了一处"。

## 五、已知取舍

- **`/tasks` 页的"AI 拆解"**：没有模型通道，保持"说明没有可用通道"（不假装拆完）。子表落地后，
  它将来接上模型时就是"往 `task_item` 插若干行"。
- **`prevState`**（勾选前状态）不落库：主表 `state` 变 `done` 后，取消完成回到 `todo` 是产品上可接受的
  简化（原型记 `data-prev-state` 是为了演示来回切）。要精确就必须加 `prev_state` 列 —— 现在不值得。
