## 二、命名规则

- 工作专属表一律 `work_` 前缀（含视图 `work_project` / `work_task`）。
- 统一层表（`project` / `task` / `project_*` / `app_user`）**不带**前缀 —— 它们被生活 / 学习共用，加了前缀就等于承诺"只此一域"。
- 索引 `ix_work_*`，唯一索引 `ux_work_*`。

## 四、逐表要点

### 4.1 `work_contact`（客户与联系人）

- `role_code` 存 code（`customer` / `colleague` / `partner`），标签留 `meta.ts`（D3）。
- `last_touch_at` 存 ISO 时刻，"上次联系 · 3 天前"是派生文案（D1）。
- `org` / `title` 分开：一家公司多个人，按 `org` 分组不靠解析字符串。

### 4.2 `work_doc` / `work_doc_link`（工作文档索引）

- **这是"外部资源登记表"，不是 Markdown 的索引** —— 正文留在公司工具，本系统只存索引、链接、脱敏摘要。它不可由文件重建，别套用"SQLite 可重建"的纪律。
- 两维不合并：`kind` = 它**是什么**（7 值，与 `project_document` 同集合），`source_code` = 它**存在哪儿**。
- `source_code` 比 `project_document` 的 4 值多：现有种子出现"公司 Wiki / 部署 · 生产 / 外部链接 / 会议纪要 / 语雀"，故取 6 值（见 `0002_work.sql` 的 CHECK）。
- `project_id` 可空：`work-docs.ts` 文件头写明这一页是**跨项目**的，允许有不属于某项目的索引。
- `work_doc_link` 是 `from → to` 的有向边，反链由查询反向扫出，不落第二份（`work-docs.ts` 的 `back` 就是这么算的）。

### 4.3 `work_okr` / `work_okr_kr`

- `objective` 与它的 KR 分成两张表（1:N），KR 带 `target_val` / `current_val` / `unit`，进度由它们算（D1），不落 `progress` 文案。
- `period` 存周期标识（`2026-Q4`），不存"第四季度"这种中文。

### 4.4 `work_time_log`（工时）

- `minutes` 存整数分钟，不存 `'1.5h'` 文案。
- `task_id` 可空：工时可以只挂在项目上、不指向具体任务。
- 判据同 D1：项目耗时、周工时全是聚合查询，不落冗余列。

### 4.5 `work_weekly_report`（周报 / 复盘）

- `period_kind` + `period_key` 唯一约束，保证"一周一份"。
- `status`（draft / published）表达是否定稿，不用 `is_done` 布尔。

### 4.6 `work_meeting` / `work_meeting_attendee`

- 参会人是多值，拆表（多值不许塞进单值列）。
- 纪要不存正文，`minutes_doc` 指向 `work_doc`（同"正文留外部"的红线）。
- 口径未决见 §九。

## 五、索引

每条对应一条真实查询：

```sql
CREATE INDEX ix_work_contact_role  ON work_contact(role_code, org);   -- 角色筛选 + 按公司分组
CREATE INDEX ix_work_doc_project   ON work_doc(project_id, kind);     -- 左栏两级目录
CREATE INDEX ix_work_doc_source    ON work_doc(source_code);          -- 按来源工具筛
CREATE INDEX ix_work_doc_link_to   ON work_doc_link(to_doc_id);       -- 反链
CREATE INDEX ix_work_okr_period    ON work_okr(period, status);
CREATE INDEX ix_work_okr_kr_okr    ON work_okr_kr(okr_id, sort_order);
CREATE INDEX ix_work_time_project  ON work_time_log(project_id, work_date);
CREATE INDEX ix_work_time_owner    ON work_time_log(owner_id, work_date);
CREATE INDEX ix_work_report_period ON work_weekly_report(owner_id, period_kind, period_key);
CREATE INDEX ix_work_meeting_start ON work_meeting(starts_at);
```

统一层的索引（`0001_init.sql`）沿用 `docs/项目表结构设计.md` §六：`(scope, …)` 打头。

## 七、与既有文档的对账

两处"同一实体、两个来源"，本设计已作结论：

1. **`task` vs `project_task`** —— 合并为一张 `task`（`docs/项目表结构设计.md` §4.3 的 `project_task` 由本文取代）。理由：任务的唯一来源应是 `task` 表；"某项目的任务" = `task WHERE project_id = ?`。拆两张会产生"工作模块读一张、项目详情读另一张"的两套账。
   - 一致性约束：`task.scope` 必须等于其 `project.scope`。跨表 `CHECK` 做不到，由写入路径校验（挂项目时同步 `scope`）。
2. **`project_document` vs `work_doc`** —— 保留两张，用途区分：`project_document`（`project_id` 必填）= 项目内的文档；`work_doc`（`project_id` 可空）= 跨项目的工作文档索引。`work-docs.ts` 文件头已明确二者不重复登记。

## 九、未决

- **`work_meeting` 是否真"专属"**：生活模块也有日程 / 家庭安排。若会被复用，应移回统一层（带 `scope`），去掉 `work_` 前缀。
- **`work_time_log` 是否真"专属"**：学习"实践项目"也要记工时。同上。
- **服务器 / 部署已建表**（`srv_*`，2026-10-14 定）：此前按"无写入方"不建，现按真实台账立项 ——
  写入路径是 `AddServerForm`，凭据存本机钥匙串不入库。详见 `../srv-design/服务器台账设计.md`。
- **`work_meeting` 归"日程事件"还是"文档纪要"**：`work-docs.ts` 里已出现"周会纪要"一条，两处口径需合一。
