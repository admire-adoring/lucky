知识库 · 数据模型与分流规则

这份是先于界面的一页验证稿：只定"数据怎么存、内容怎么流转"，不定视觉。 落地时最贵的返工来自数据结构，界面反而是最便宜的部分。

1输入与它带来的硬约束

你给的两个事实（双链是核心用法 / 上千条量级）会改变结论，逐条列出它们推出的要求 —— 后面所有字段与规则都是为满足这几条。

输入推出的硬约束做不到会怎样
双链是核心 链接表是一等公民；必须能列出"谁引用了我"；必须有链接建议与孤儿巡检 靠人肉回忆补链接 → 120 条以上就没人补了，加工层永久堆积
上千条 检索是主入口，浏览是次要入口（分区 + 视图解决"看哪些"，搜索解决"找那条"） 用列表翻 1000 条 = 不可用
列表必须游标分页 + 排序 + 多条件筛选，不能一次渲染全量首屏几秒白屏
成熟度必须自动推导，且要能批量处置12 条未链接能手改，120 条就只能放弃
图谱不能画全库：默认画"以某条笔记为中心 N 跳"的局部图，全库只给统计与聚类1000 个节点 + 3000 条边的全图 = 一团毛线
归档与收件箱必须有自动化（只进不出 + 无自动清理 = 垃圾堆积）三年后库里有 3000 条，其中一半是死的
由此撤掉的两个之前的假设
  • 原型里"主题只有 42 个、平铺即可"不成立：上千条下主题会涨到上百个，必须支持分组（见决策 4）。
  • 原型里"标签点一下就筛"不够：几百个标签需要治理（合并同义、淘汰废弃），否则筛选器本身变成噪音。

2实体与字段

7 个实体。主键 外键；"冗余列"指为性能而存、可重算的字段。

3七个关键决策（含判据与反面后果）

这一章是全文最该被质疑的部分。每条都给出判据与"不这样做会怎样"，你可以逐条推翻。

决策 1 · 收件箱是 note 的一个状态，不建独立表

判据：从收件箱进主库是状态迁移（补 topic_id / 改 stage），不是"搬家"；同一条笔记的 id 必须全程不变，否则双链、附件、历史会断。

反面：做成 inbox_item 表后，"归类"要 delete + insert，link 表外键要级联改，附件的 note_id 要迁移，还会出现"同一内容两个 id"的历史断点。

决策 2 · stage 与两个 link 计数存成冗余列，由规则重算

判据：上千条下，列表要按 stage 筛选 + 排序 + 分页。纯派生意味着每页查询都要实时聚合 link 表算入链数；规则一改还要改所有查询。冗余列让"筛未链接"变成走索引的一次查询。

代价与对策：冗余会不一致。对策是三条 —— ① 所有写操作走同一个写入路径（链接增删时同事务更新计数）；② 每日全量重算并输出差异报告；③ 差异 > 0 就告警，不允许静默飘移。

决策 3 · link 一行表示一条有向关系，不存反向行

判据：存反向行意味着"删一条链接要删两行、改一行要保证两行一致"。上千条下 link 表约 3–5 千行（1240 × 3.4），远小于笔记表，双向查询用 WHERE from = x OR to = x + 两个索引就够快。

反面：双向存两份 → 迟早出现"单向幽灵链接"（A 说链了 B，B 看不到），图谱与入链计数全部不可信。

决策 4 · 主题支持一层父子，禁止无限层级

判据：上千条下主题会从几十涨到上百个，平铺不可扫；但"主题套主题套主题"会变成第二个标签体系，而且圆盘、筛选器、面包屑都只能呈现三层以内。

落地形态：parent_id 为空 = 领域主题（前端工程化 / 后端架构 …），非空 = 该领域下的分组（构建 / 状态管理 …）。层级深度在写入时校验，只允许 2 层。

决策 5 · 标签靠合并与淘汰治理，不做层级

判据：标签是自发涌现的，唯一可持续的控制手段是"降熵"：alias_of 合并同义（React / react / React.js → 一个），last_used_at 淘汰废弃。软约束：一条笔记 ≤ 3 个标签，超了就说明该建主题了。

反面：给标签建层级 = 和主题重复，之后每次都要判断"这条到底进主题还是进标签"。

决策 6 · 归档规则只产出候选清单，不静默执行

判据：自动归档 = 自动把内容从检索里拿掉。上一轮我已经把"两周未动自动归档"标为危险默认 —— 唯一可接受的例外是收件箱：它本来就是"未整理"的临时区，可以自动归档，但必须在收件箱顶部留一条"已自动归档 7 条 · 撤销"的记录。

主库永不自动归档：只给"归档候选"清单（如 12 个月 0 入链且无标签），人工确认后执行。

决策 7 · 检索必须支持结构化谓词，且是主入口

判据：上千条下"找那条"不可能靠浏览。可组合的谓词把"我上次写的那条关于支付的"变成一条查询。

语法（v1）：tag:架构 · topic:后端架构 · stage:process · has:inlink · has:nolink · source:clip · before:2026-06，与关键词混合（如 对账 topic:后端架构 has:inlink）。

决策 8 · 知识库不存复习状态

判据：到期日与掌握度绑在"学习目标"上，与"内容归属"无关。知识库只留 last_viewed_at（服务"最近"），一旦把 SRS 状态也存进来，同一条笔记就会有两个状态的真相源。

4状态机与分流规则

四个状态、五个迁移动作。每一步都能回答"这条笔记现在该做什么"。

4.1 四个状态

record 记录 → process 加工 → produce 生产 ／ archived 归档 ／ returned 退回来源
状态由字段推导，不是人工选择；人只改字段（归类 / 点亮常青 / 归档），状态跟着变。

4.2 状态推导（机械判据，可直接写成 SQL）

状态判据含义（对应你那张图的症状）
recordarchived_at IS NULL AND topic_id IS NULL记录层：还没加工（"漏"）
processtopic_id IS NOT NULL AND link_in_count = 0 AND NOT is_evergreen加工层：归类了但没被引用（"懵"）
producelink_in_count > 0 OR is_evergreen生产层：可被检索、可被引用（"调得出来"）
archivedarchived_at IS NOT NULL冻结：不参与检索与图谱（优先级最高，先判它）

4.3 迁移动作（谁能触发，触发后发生什么）

动作触发者写入连带
捕获人工 / 剪藏插件建 note，inbox_status='unfiled'写一条 stage_log（null → record）
归类到主题人工（或 AI 建议后人工确认）补 topic_id，清空 inbox_statusrecord → process；topic.note_count +1
补链人工 / 链接建议一键接受插 link，更新两侧计数若被引用方原为 process，升为 produce
点亮常青人工is_evergreen = true升为 produce（这是"我认它够格"的唯一人工升级口）
归档人工（候选清单确认后）archived_at = now()从检索与图谱摘除；入链计数保留但不再参与"未链接"统计
恢复人工archived_at = NULL按 4.2 重新推导 state
退回来源人工（收件箱行内）删除本库 note，写 stage_log 留痕同时在学习 / 工作模块建对应笔记（先建后删，避免中途失败丢内容）

4.4 三个断裂点的指标口径（与界面上的 KPI 一一对应）

指标口径界面
漏count(stage = record)收件箱计数、KPI 第一张卡
懵count(stage = process)「未链接」视图、右侧轨、KPI 第二张卡
调不出来count(link_in_count > 0) / count(*)，排除已归档KPI 第三张卡（274 / 1240 这类分式）

4.5 双链是核心 ⇒ 必须有三个自动化（否则上千条下必崩）

机制判据交互
链接建议同 topic 且共享 ≥2 个 tag；或正文关键词重叠高于阈值（用全文索引打分近似）在笔记详情里给"建议链接"列表，一键接受 / 忽略
黑洞巡检入链 ≥3 但出链 = 0列进"待补出链"，避免只进不出的吸附点
孤儿巡检入链 = 0 且出链 = 0 且创建 ≥30 天和「未链接」视图合并展示，但按"完全孤立"优先排序

4.6 收件箱的自动分流（上千条下唯一可行的整理方式）

  • 剪藏类自动抽标题、摘要、建议主题与 1–3 个标签（AI 产出，人工确认才落库 —— 不自动改 topic_id）。
  • 同一来源连续 ≥3 条：提示批量归类（"这批 5 条都来自《反脆弱》，一起挂到「读书笔记」？"）。
  • 14 天未动：进"自动归档候选"；收件箱顶部显示"已自动归档 7 条 · 撤销"，不静默。
  • 退回来源：命中"删掉来源后不成立"的（判据见 4.3），一键退回学习 / 工作模块。

5上千条下的检索与性能

量级一变，入口就变：浏览让位给检索。这一章是"能不能用"的分水岭。

5.1 查询模式与上限

场景查询上限 / 策略
分区首屏按 (archived_at, updated_at) 取首页20 条 + 总数；游标翻页，不用 offset
视图筛选加 stage / link_in_count 条件同上；筛"未链接"必须走索引，不许全表扫
检索 ⌘K全文 + 谓词组合结果 20 条 + 高亮；标题权重高于正文
局部图谱以某笔记为中心 1–2 跳节点 ≤ 60、边 ≤ 200，超出按入链数截断
全库图谱不画图，只出统计孤立笔记数、平均入链、最大聚团大小
主题 / 标签列表按 note_count 倒序只取前 100；更深的用检索谓词

5.2 中文全文索引

坑

默认分词对中文不可靠：分词器把「对账」切成一个字 就导致搜不到。v1 至少用 trigram（三字滑窗） 或成熟中文分词器，并在写入时把 title 与 body 分别索引、分别加权。

5.3 冗余与一致性

冗余字段来源何时重算
note.stage4.2 的判据相关字段变更时同事务；每日全量校验

6迁移、重算与治理

项做法频率
结构版本schema_version 表 + 按序号命名的迁移脚本；每次迁移必须可回滚每次改结构
状态重算跑 4.2 判据全量重算，输出"变化条数 + 前后分布"报告每日 + 规则变更后
标签治理合并（写 alias_of，历史引用保留）/ 淘汰（note_count = 0 且 90 天未用）/ 归一（全半角、大小写）每月
主题治理主题数 > 60 提示分组；note_count = 0 的空主题进清理候选每季
归档回顾生成候选清单（12 个月 0 入链且无标签 → 归档；候选被忽略 3 次则不再提示）每季
只进不出的代价，必须有出口

知识库"只进不出"说的是不删除，不是"不整理"。上千条量级下没有出口的后果是：五年后 5000 条里一半是死的，检索信噪比崩掉。所以出口是归档 + 季度回顾，而不是删除。

7本阶段明确不做

不做理由留的口子
多人协作与权限先验证"一个人会不会天天用"表都带 owner_id 位置，后加不迁移数据
向量检索 / 语义问答成本高，且先要有稳定的结构化检索预留 note.embedding 可后加，不影响现有字段
附件在线预览 / OCRv1 只要"能存、能点开原图"attachment 表已独立，不塞进 body
从 Obsidian / Notion 导入v1 用剪藏 + 手工录入即可留 import 适配层位置（source 枚举已含扩展位）

8原型要跟着改的 6 处（下一步的清单）

现在的原型是"286 条 + 双链为装饰"的心智，与你确认的"上千条 + 双链为核心"不一致。下列 6 处是数据模型定稿后要改的界面部分。

#改什么为什么（对应约束）
1数字上调：286 → 1240；主题 42 → 96（含 3 个分组）；标签 96 → 280；双链 348 → 4200（链/笔记 ≈ 3.4）数量级影响所有判断
2图谱：全库图 → 「以当前笔记为中心 2 跳」局部图；顶部补全库统计（孤立 37 条 / 平均入链 2.1 / 最大聚团 180）1000 个节点画成一张图毫无信息量
3⌘K 从"导航面板"升级为检索面板：输入即出结果列表（标题 + 摘要 + 命中位置）；导航项只在无输入时显示检索是上千条下的主入口
4列表加：游标分页提示（已加载 20 / 1240）、排序切换、多条件筛选（stage / 标签 / 有无入链）浏览不再是主要用法
5收件箱加：批量选择 + 批量归类；整理规则里"两周未动自动归档"改成"生成归档候选清单 + 撤销"决策 6：不许静默丢内容
6主题与标签加治理入口：主题分组折叠、空主题清理、标签合并与废弃上百主题 / 数百标签必须能降熵
确认这份模型之后，我建议的第一件实现

只做一条纵向切片：捕获 → 收件箱 → 归类到主题 → 笔记列表（分页）→ 补一条双链 → 入链计数与状态跟着变。 这条链把 7 个实体里的 4 个（note / topic / link / stage_log）和两个冗余重算都跑通了，是"模型能不能用"的最小验证；其余分区可以先留空壳。
